# Universal media-artifact model — design

> **Status:** schema + adapter shipped (`cli/lib/schemas/media-artifact.ts`); eval + distribution are seams, not integrations. No project storage was migrated.
> **Tracks:** [`../../notes/issues/done/461-universal-media-artifact-model.md`](../../notes/issues/done/461-universal-media-artifact-model.md)
> **Grounded as of:** 2026-06-23 against the live repo. Path/primitive citations below were verified to exist at that time.

Read [`../../CLAUDE.md`](../../CLAUDE.md) (the `.ralphy/` layout + the `artifacts/<kind>/` taxonomy) and [`../../AGENTS.md`](../../AGENTS.md) invariant #14 (append-only) for the surrounding context. This is schema/adapter work, deliberately: the issue's own note says do NOT rewrite all project storage in one risky migration. The model is a descriptor and a read-only adapter, nothing more.

---

## 1. Goal & non-goals

### Goal

Give projects, Units (#069), provenance (#420), eval, and distribution (#458) one stable shape to describe ARBITRARY media outputs — audio-only cuts, slide decks, documents, interactive/WebGL scenes, mixed deliverables — without hardcoding every workflow to `mp4` / `png`. Each new open-world mode (#454) otherwise reinvents its own folder conventions, metadata, eval rules, and packaging.

### Non-goals

- **Not a storage migration.** No project files move. No `unit.json` is rewritten. The adapter reads existing manifests; it does not produce new on-disk state.
- **Not a CLI verb.** This round ships the schema, the capability maps, and the Unit adapter only. No command is registered; `cli/index.ts` is untouched.
- **Not eval/distribution integrations.** The capability maps are DATA the gate registry and the distribution packer READ. The scorers and packers themselves are out of scope here.

## 2. Taxonomy (acceptance 1)

`MediaArtifactKind` (`MEDIA_ARTIFACT_KINDS`) is the universal kind enum. It is a SUPERSET of the project `artifacts/<kind>/` directory taxonomy (`images|videos|voiceover|music|sfx|captions|fonts|refs`): those eight production-input kinds collapse into the output-facing kinds below, and the model adds the open-world kinds the directory taxonomy never had.

| Kind | Covers | `artifacts/<kind>/` it generalizes |
|---|---|---|
| `image` | a single still | `images` |
| `video` | a moving-image cut | `videos` |
| `audio` | voiceover / music / sfx / podcast cut | `voiceover`, `music`, `sfx` |
| `captions` | a timed text track (standalone or attached) | `captions` |
| `document` | a paged/flow document (pdf/md/html-doc) | — |
| `slide-deck` | an ordered slide set (carousel, pitch deck) | — |
| `html-interactive` | interactive HTML / WebGL / 3D / game-like preview | — |
| `data` | a structured data file shipped as output | — |
| `ref` | an INPUT reference the output was produced against | `refs` |
| `package` | a bundle of other artifacts (a distribution pack) | — |
| `custom` | extension escape; concrete label in `customKind` | — |

The enum is append-only — downstream eval/distribution maps key off these strings, and a renamed/repurposed member breaks them silently. `custom` is the pressure valve: a kind the taxonomy has not grown yet ships as `{ kind: "custom", customKind: "<label>" }` (a `.refine()` enforces the label), so a new mode never has to fork the enum to ship.

Why a superset and not a re-use of the directory taxonomy: the `artifacts/<kind>/` dirs are PRODUCTION-INPUT bins (`voiceover` vs `music` vs `sfx` are three folders because they are generated by three different `ralphy generate` verbs), whereas the artifact model is OUTPUT-FACING (all three are one `audio` kind for eval + distribution purposes — they get the same audio scorers and the same packaging). Collapsing them at the model layer is deliberate; the folder split stays where generation needs it. `fonts` has no artifact kind because a font is never a shipped deliverable on its own — it is a sub-resource of an image/video/deck.

## 3. Metadata contract (acceptance 2)

`MediaArtifactSchema` carries: a location (`uri` OR `path` — a `.refine()` requires exactly one of them present), `mime`, `durationMs`, `width`/`height`/`aspect`, `bytes`, `textTracks[]`, a production `role` + `slot` + `id`, generation attribution (`model` / `provider` / `costUsd`), and a `provenance` block (#420 links: `sourceArtifacts`, `template`/`style`/`recipes`/`assets`, `provenanceGraph`). Every field but `kind` and the location is optional + additive, so a partially-known artifact still parses and an older serialized artifact never fails validation.

The `uri`-OR-`path` split is the storage-agnostic seam called out by the cloud-factory design (#462 §4 "Artifact"): `path` is the local-first project-relative form; `uri` is an object-store key / remote URL. The contract never bakes in a local absolute path, so the same shape survives the move from `.ralphy/` files to signed object-store URLs.

`MediaArtifactSetSchema` is the ordered, heterogeneous bundle — the multi-kind generalization of a deliverable's media list, with an optional explicit `order[]` (by `id`/`slot`) on top of array order.

`parseMediaArtifact()` / `parseMediaArtifactSet()` are the validate-and-throw entry points (ZodError → callers map to `E_VALIDATION_FAILED` with `error.message` as `detail`).

A fully-described video cut, for reference:

```json
{
  "version": 1,
  "kind": "video",
  "path": "render/final.mp4",
  "mime": "video/mp4",
  "durationMs": 31000,
  "width": 1080, "height": 1920, "aspect": "9:16",
  "role": "hero", "slot": "scene-04",
  "model": "kwaivgi/kling-v3.0-pro", "provider": "openrouter", "costUsd": 0.42,
  "textTracks": [{ "kind": "captions", "path": "captions/scene-04.srt", "format": "srt", "language": "en" }],
  "provenance": { "template": "choose-path", "style": "ps1-horror", "recipes": ["vhs-grain"], "provenanceGraph": "provenance.json" }
}
```

## 4. Unit integration (acceptance 3)

This model does NOT replace [`../../cli/lib/schemas/unit.ts`](../../cli/lib/schemas/unit.ts). A `UnitManifest` stays the curated, ordered, append-only deliverable; a `MediaArtifact` is the richer per-output descriptor. The two relate one-way: a Unit's media maps INTO artifacts, never the reverse.

The integration seam is `mediaArtifactFromUnitMedia(unit)`. It is the only coupling point, and it is read-only:

- It walks `unit.media[]` **in order** — a Unit's ordering, the thing #069 guarantees, is preserved exactly.
- Each filename becomes an artifact with `path` = the verbatim unit-relative filename (the file is not moved), `id`/`slot` = that filename (the manifest's stable key).
- `kind` resolves from `unit.media_meta[filename].kind` when present, else from the file extension (`inferKindFromFilename`), else `image` (the historical Unit default).
- `aspect` carries over from `media_meta`.
- The Unit's block-level `provenance` (`template`/`style`/`recipes`/`assets`) plus the `provenance_graph` pointer are lifted onto every artifact's `provenance`.

`unit.ts` is imported type-only (`import type { UnitManifest }`), so there is no runtime coupling and no circular-import risk — the same load-order discipline `workflow.ts` documents for its contract pin.

## 5. Eval mapping (acceptance 4)

`EVAL_CAPABILITIES: Record<MediaArtifactKind, EvalCapability[]>` maps each kind to the quality-check AXES that even apply to it (`visual` / `motion` / `audio` / `text` / `timing` / `structure`). A gate registry reads the flags and picks its scorers — there is no point running a retention/motion check on a `data` file, and a `ref` is `[]` (an input is not eval-gated). This is the data seam #461 acceptance 4 asks for; the scorers stay where they are (`cli/lib/eval/`). Append flags as new check families land.

## 6. Distribution mapping (acceptance 5)

`DISTRIBUTION_CAPABILITIES: Record<MediaArtifactKind, DistributionCapability[]>` maps each kind to HOW it can be packaged + placed (`feed-post` / `story` / `attachment` / `download` / `embed` / `source-only`). A distribution pack (#458) reads these to decide what belongs in a pack and what platform-manifest entry to emit — captions ride as an `attachment`, a `ref` is `source-only` (never distributed), an `html-interactive` is `embed`. Again DATA, not an integration.

## 7. Migration plan — non-breaking (acceptance 6)

The migration is "describe, don't move":

1. **Nothing on disk changes.** No project storage migration, no `unit.json` rewrite, no new persisted file. Append-only history (AGENTS.md #14) is untouched because the only coupling — `mediaArtifactFromUnitMedia` — is read-only over the manifest.
2. **Current manifests map in today.** Any existing `unit.json`, including legacy ones with no `media_meta`, produces a valid `MediaArtifact[]` via the adapter (extension inference covers the gap). The test suite proves this against manifests parsed through the live `UnitManifestSchema`.
3. **Adoption is opt-in and incremental.** A future eval/distribution/cloud caller consumes `MediaArtifact[]` by calling the adapter at the boundary; it does not require any writer to start emitting the new shape first.
4. **When a writer DOES adopt it** (e.g. a future asset manifest emitting artifacts directly), it persists `MediaArtifactSet` as a new sibling file — never overwriting `unit.json`, consistent with the append-only contract.

## 8. Fixtures (acceptance 7)

Covered in [`../../tests/unit/media-artifact.test.ts`](../../tests/unit/media-artifact.test.ts) — schema round-trip + defaults, the `uri`-only storage-agnostic form, bad-kind + missing-location + `custom`-without-label rejection, the capability maps (every kind has an entry; `video` is motion/timing-gated, `ref` is source-only), and the Unit adapter against manifests validated through the real `UnitManifestSchema`:

- **Video Unit** — `final.mp4` + `thumb.png` with `media_meta` + full provenance → ordered `[video, image]` artifacts carrying the lifted provenance + graph pointer.
- **Image pack / legacy Unit** — no `media_meta`, mixed extensions → kind inferred per file.
- **Audio-only clip pack** — `podcast-cuts` of `.mp3` files → `[audio, audio]` (extension inference, since `unit.ts` `media_meta.kind` is `image|video` only today).
- **Bare Unit** — no provenance → artifacts with no provenance block.

The carousel / HTML-motion-design fixtures the issue lists are exercised at the kind level via the taxonomy + capability-map tests (`slide-deck`, `html-interactive`); a Unit-side fixture for them follows once `unit.ts` `media_meta.kind` grows past `image|video` — a one-line extension to `unitMediaKindToArtifactKind`, which is why that indirection exists.

## What this does NOT decide

The `unit.ts` `media_meta.kind` enum stays `image|video` this round (no schema edit to an existing file). Whether an asset manifest or a distribution pack ever PERSISTS `MediaArtifactSet` is deferred to #458. The scorers behind the eval flags and the packers behind the distribution flags are out of scope. The only commitment here is: one storage-agnostic descriptor, one read-only Unit adapter, and two capability maps as data — so the open-world modes (#454) and the cloud port (#462) wrap this shape instead of forking it.
